# 06-环节技术实现总览

> 本文梳理千里单骑自动化全流程中**每个环节的识别与动作技术形式**。
> 判据以 `src/game/runner.py::classify` / `_act_*` 与各决策模块为准（2026-10-08 核对）。
> 历史事故与教训见 `.workbuddy/memory/`，策略规则见 `docs/02`，OCR 关键词见 `docs/04`。

## 一、五种技术手段

| 手段 | 说明 | 适用场景 | 成本 |
|---|---|---|---|
| **A. 固定坐标点击** | 不做识别，直接 `tap(x,y)` | 位置恒定的按钮（取消/下一步/返回等） | 零 |
| **B. OCR 关键词锚定** | 整屏 OCR → 匹配已标定关键词 → 命中即分类 | 界面有独特文字锚点 | ~1–2s/次 |
| **C. OCR 实时定位点击** | OCR 找到关键词的**文字框中心**再点击 | 按钮/武将名位置会变（奖励按钮、货架、武将名） | ~1–2s/次 |
| **D. 模板匹配** | 灰度 `TM_CCOEFF_NORMED` 多目标 + NMS | 外观固定的美术元素（节点图标、任务按钮横幅） | ~40ms/次 |
| **E. 结构计算** | 霍夫圆 + 列聚类 + 假圆过滤 | 地图节点（无文字、位置固定但类型多变） | ~0.5s/次 |

原则：**A 优先于 D，D 优先于 B/C**——能写死坐标不加识别，能模板匹配不用 OCR。

### 2.6 容错机制（横切）

| 机制 | 触发 | 行为 | 事故来源 |
|---|---|---|---|
| unknown 容忍 | 未知界面（无论有无文字） | 等待重看，连续 12 帧（~30s）才停机存图 | 过渡帧×2 形态 |
| 托管重试重分类 | 托管验证失败 | 每轮重看屏幕：不再是 battle 即交回主流程 | 过渡帧误判 |
| 超步数跳局 | 单局 >2000 步 | 跳过该局继续下一局（不连坐） | 无尽深层长局 |
| 局部轮询 | 托管等待 | 只扫右上区域（取消托管按钮）+底部流程锚点，按钮消失/锚点命中即交回 | 完胜页 HUD 残留 |
| 假收官防护 | in_run 标记 | 未进过局内状态时忽略结算浮层 | 遗留浮层 |
| 任务巡检异常隔离 | 巡检抛异常 | 吞掉+兜底返回，不影响主流程 | — |
| 看门狗 | 每 180s | faulthandler dump 全线程堆栈到 runtime/hang_dump.txt | 推理挂死 |
| 热重载 | GUI 每次启动 | importlib 重载全部游戏模块 | 改代码不生效 |

## 三、性能关键点

| 优化 | 收益 |
|---|---|
| OCR 线程限制 intra=2 | 不再占满全核饿死模拟器（挂机越跑越慢的根因） |
| 托管等待局部轮询 | 等待期检查 2–6s → 0.75s |
| 任务按钮模板匹配 | 2s(OCR) → 40ms/次，4 按钮巡检 24s → 11s |
| 每帧 OCR 缓存（GameContext.ocr_items） | 14s/轮 → 3.5s/轮 |
| **截图 raw 模式**（`exec-out screencap` + RGBA2BGR） | 1.03s/帧 → 0.47s/帧（设备端 PNG 压缩是大头） |
| **锚点表**（区域化小模板，13 条目） | 已知页面判页 1.9s(整屏 OCR) → 12–25ms |
| **操作序列**（结算/开战合并成单动作） | 每场战斗少 3–5 个主循环 |
| **OCR 结果按帧缓存**（OCREngine，对象身份） | 同帧重复读取 3 次 2869ms → 0ms |
| **灰度图按帧缓存**（`runner._gray`） | 每步省 3–5 次重复 cvtColor |
| **GUI 日志批量写入 + 环形上限** | 每行 4 次 Tk 调用 → 整批 1 次；行数封顶 2000 |
| **GUI 状态变化才刷新** | 空闲轮询 600ms、运行 150ms，避免无意义重绘 |
| OCR 线程等待策略 PASSIVE（OMP/KMP 环境变量） | 空闲不自旋抢核（与模拟器共存更稳） |
| **OCR GPU 推理**（DirectML，2026-11-12） | 整屏 OCR **864ms/2.77s CPU → 180ms/0.24s CPU**（4.8 倍、CPU 占用降 11 倍）；无 GPU 自动回落 CPU |
| **识别设备切换**（auto/cpu/dml） | `ocr.device` + GUI 下拉框；DML 初始化失败自动回落 CPU |

## 3.1 GUI 分层（2026-11-12 重构）

参考一条龙「界面与业务解耦」的做法，GUI 拆成两层：

- `src/gui/app.py` —— **控制器**：收集配置、起停工作线程、轮询队列；
  不直接操作 Text/变量。
- `src/gui/widgets.py` —— **视图控件**：`LogView`（批量追加、环形上限、
  智能吸底）、`StatusPanel`（变化才写回 Tk 变量）、`plan_log_append`
  （纯函数，可离线单测）。
- 业务层 `src/game/runner.py` 完全不知道 GUI 存在，`run_auto` 只通过
  `status_cb` 回传统计，因此可以脱离界面跑测试与 CLI。
