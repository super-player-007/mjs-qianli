# 03 · 坐标系与适配说明

## 1. 坐标系定义

| 项 | 值 |
|---|---|
| 坐标系原点 | 屏幕**左上角** (0, 0) |
| x 方向 | 向右为正 |
| y 方向 | 向下为正 |
| 单位 | 像素（px） |
| **标定基准分辨率** | **1920 × 1080** |
| 基准 DPI | 280 |
| 模拟器实际分辨率 | 1920 × 1080（与基准一致 → 当前缩放比 = 1.0） |

> 所有 `config/coords.yaml` 中的坐标**一律以 1920×1080 记录**，不要写实际分辨率。若日后更换模拟器分辨率，运行时自动等比缩放，无需手改。

---

## 2. 适配规则

运行时由 `src/common/utils.py::scale_point` 统一换算：

```
sx = 实际宽度 / 1920
sy = 实际高度 / 1080
X_实际 = round(X_基准 × sx)
Y_实际 = round(Y_基准 × sy)
```

矩形区域用 `scale_box`（对左上、右下两点分别换算）。

**注意**：等比缩放只保证"位置大致对得上"。若宽高比不同（如 16:10 vs 16:9），模板匹配需重新采集模板；按钮坐标则可继续沿用缩放值。

当前基准与实际一致，缩放比为 1.0，**不存在换算误差**。

## 3. 坐标表格式（config/coords.yaml）

```yaml
screens:
  <屏幕标识>:
    <元素名>:
      type: point                 # 单点点击
      xy: [960, 585]
      desc: "说明"

    <元素名2>:
      type: region                # 区域：模板搜索 / OCR 裁剪
      box: [660, 480, 1260, 560]
      desc: "说明"

    <元素名3>:
      type: swipe                 # 滑动轨迹
      path: [[960, 800], [960, 300]]
      desc: "说明"

    <元素名4>:
      type: options               # ★决策点：一组可选项中心点
      points: [[960, 400], [960, 620], [960, 840]]
      desc: "增益三选一的可点位置"
```

补充可选字段：
- `template: "battle_result/continue"` —— 若填写，优先在该元素区域内做模板匹配，命中的实际位置会覆盖 `xy`（更抗 UI 微调）
- `weight: 3.0` —— 决策点选项的显式推荐权重（覆盖关键词打分）

## 4. 标定流程

```bash
# ① 进入目标界面后，抓一张带网格的截图
.venv/Scripts/python.exe run.py capture --count 1 --grid --step 100 --tag <界面名>

# ② 打开截图，按网格读出目标元素的像素坐标
#    网格每 100px 一条线，并标注了坐标值

# ③ 填入 config/coords.yaml
# ④ 用离线识别验证（不碰游戏）
.venv/Scripts/python.exe run.py analyze --image <截图> --templates
```

**安全提示**：标定全程只用 `capture / analyze / observe`，这三个命令**不会点击游戏**。

#### 节点类型识别（`run.py nodes`）

节点**位置固定、类型与数量每层变化**，所以必须识别。实现见 `src/game/node_icon.py`：

1. **定位**用霍夫圆（`dp=1.2, minDist=120, param1=120, param2=34, r∈[36,62]`）。
   与类型无关，找几个就是几个。
   ⚠ param2=40 会**漏掉篝火（休息）节点**（它的圆边缘对比度比头像弱），
   2026-09-17 第 3 层实测必须 34；多出的假圆由深色图标判据 + 列聚类兜住。
   实测圆心：第 1 层 `(667,397)(667,567)(668,736)`、第 2 层 `(1082,397)(1081,567)(1082,736)`、
   第 3 层 `(1101,395)(1105,565)(1099,731)`，`r≈44~52`。
2. **分类用双窗口**（节点有两种画法）：
   - **头像节点**（战斗/商店/事件/武将/伙伴）：圆里是武将头像，类型图标在圆下方，
     取「圆心 +`(+5,+48)`」处 `35x30` 窗口比对，且该处须有深色字形（假圆闸）；
   - **本体节点**（休息=篝火）：圆里**就是**图案，圆下无图标，
     改比对**圆内** `88x88` 窗口（模板 `64x64`）。

| 类型 | 画法 | 图标 | 状态 |
|---|---|---|---|
| `battle` | 头像节点 | 双刀交叉（圆下） | ✅ `node_battle.png`（2026-09-16） |
| `shop` | 头像节点 | 铜钱串（圆下） | ✅ `node_shop.png`（2026-09-17 第 3 层） |

| `hero` | **本体节点** | 圆内即事件人物 | ✅ 按事件存模板（2026-09-17 第 4 层） |
| `mate` | **本体节点** | 圆内即事件动物 | ✅ 按事件存模板（2026-09-17 第 4 层） |

**⚠ 武将/伙伴是"本体节点 + 按事件存模板"**：第 4 层实测 1【十二阉人事件】、
3【墨家巨子】都是武将节点、2【小狗当道事件】是伙伴节点，三者圆下都**没有**类型图标
（圆内即画面）。且两个武将事件画面完全不同（互配仅 **0.35**），单一 hero 模板打不通
→ 命名 ``node_<类型>_<事件>.png``（如 `node_hero_shier.png`/`node_hero_moja.png`/
`node_mate_dog.png`），加载时按**第一个下划线前缀**归类（`node_icon.template_kind`），
分类时同类型取最高分。**遇到没见过的事件 → unknown → 暂停问用户，裁模板即插即用。**

**实测分数**：正确类型 `0.85~1.00`，非节点区域最高仅 `0.48~0.76`（图例栏/印章处，管线采不到）
→ 阈值 `0.70` 分离干净。第 3 层交叉干扰：头像圆内窗对图标模板 ≤0.54。
`assets/templates/run_map/_ref_legend/` 里存着用户给的图例图标，**别拿来当模板**（见下面坑）。

> ⚠ **踩过的坑：图例栏的图标不能当模板。**
> 顶部图例与节点图标**同形但不同底**（图例是深蓝灰木牌底、节点是米色卡底），
> 拿图例图标去匹配节点最高只有 **0.358**，不可用。
> 正确做法：**从游戏截图的真实节点上直接裁**那块图标。
>
> ⚠ **比对窗口边距不能抠。** 边距不足会让模板在滑动窗口里被裁掉一行、分数虚低
> （实测 node3 由 0.857 掉到 0.659，差点贴阈值误判）。当前取 `ICON_MARGIN=14`。
>
> ⚠ **已通关印章不可识别。** OCR 读成「巨通关」、红色色彩特征分不开、印章模板全图 -1.000，
> 三条路全断（详见 `_deprecated/templates/`）。当前层过滤（列聚类）顺带解决了它。

**新增类型**：把从真实节点裁下的图标存成 `assets/templates/run_map/node_<key>.png`，
`src/game/node_icon.py` 自动加载，无需改代码；中文名在 `NODE_LABELS` 补一行。

> ⚠ **点击节点 = 进入该节点（战斗则开打），属决策点。**
